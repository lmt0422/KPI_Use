# AWS S3 Deep Archive リストア運用に関する改善説明書

## 1. 背景と目的

現在使用しているS3 Deep Archiveの一括リストア申請スクリプトにおいて、「ファイルの現在の状態を確認せずに無条件でリストアを申請する」というロジックに起因する運用上の課題が発見されました。

本ドキュメントでは、既存スクリプトの課題（なぜ事前にステータスを確認する必要があるのか）を整理し、それを解決するための改修内容とその効果について説明します。

## 2. 既存スクリプトの課題：なぜ「事前ステータス確認」が必須なのか？

S3の仕様上、オブジェクトの現在の状態を無視して盲目的にリストア（解凍）処理を実行すると、以下の3つの重大な問題が発生します。

### ① 重複申請によるエラーと制限のリスク

* **課題**: オブジェクトがすでに「リストア処理中（Restoration in progress）」であるにもかかわらず、再度リストア申請を送信すると、APIがエラーを返すか、システムによっては無駄なリクエストが滞留する原因となります。
* **影響**: エラーログが大量に発生し、本当に失敗した申請と区別がつかなくなります。

### ② ステータスの不可知性による大幅な時間のロス

* **課題**: 以前発生した `Object is of Storage class GLACIER` というエラーが示す通り、現在のストレージクラスを把握することは重要です。もし対象のファイルがすでにリストア済みで「Standard（標準）」クラスに戻っている場合、本来であれば**すぐにダウンロードやRDSへのインポートが開始できる状態**です。
* **影響**: 確認を怠り再度リストア申請のフローに乗せてしまうと、必要のない「解凍待ち時間（通常12時間程度）」が新たに発生し、作業スケジュールに致命的な遅延をもたらします。

### ③ コスト管理（無駄な費用の発生）

* **課題**: S3 Deep Archiveからのデータ取り出し（リストア）には、データ量とリクエスト回数に応じた従量課金が発生します。
* **影響**: すでにリストア済みで有効期限内のファイルに対して、無条件に重複リクエストを送信し続けることは、不要なインフラコストを継続的に発生させることになります。

---

## 3. 解決策：ステータス駆動型のリストアロジックへの改修

上記の課題を解決するため、スクリプトに「事前チェック（Pre-Check）」のロジックを追加する改修を行いました。

### 変更後の処理フロー

新スクリプトでは、`aws s3api restore-object` を実行する前に、必ず `aws s3api head-object` を呼び出して対象ファイルのメタデータを取得し、以下の3つの状態に分類して処理を分岐させます。

1. **READY（リストア完了・即時利用可能）**
* **判定条件**: `ongoing-request="false"`
* **アクション**: **[SKIP]** リストア申請を行わず、スキップする。そのままRDSインポート等の次の作業へ移行可能。


2. **IN_PROGRESS（リストア処理中）**
* **判定条件**: `ongoing-request="true"`
* **アクション**: **[WAIT]** 重複申請を防ぐためスキップし、AWS側の処理完了を待機する。


3. **NOT_STARTED（リストア未申請 / GLACIER状態）**
* **判定条件**: Restoreステータスが存在しない
* **アクション**: **[ACTION]** ここで初めて `restore-object` APIを呼び出し、リストア申請を実行する。



---

## 4. 期待される効果（まとめ）

この「確認してから実行する」という冪等性（何度実行しても結果が同じになる性質）を持たせた設計により、以下のメリットが得られます。

* **作業の安全性向上**: エラーを未然に防ぎ、ログの可読性が大幅に向上します。
* **ダウンタイムの最小化**: すでに利用可能なファイルを即座に判別できるため、DBAのテスト・移行作業を最短ルートで進めることができます。
* **コストの最適化**: AWSに対する無駄なAPIリクエストや、重複する取り出し料金の発生を完全に防止します。
